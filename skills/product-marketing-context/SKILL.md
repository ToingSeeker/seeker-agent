# Product Marketing Context

## When to use
- Before any recurring marketing work (copy, campaigns, pages, plans), so each task does not re-ask the same questions.
- When positioning has changed: new segment, pricing, major feature, new competitor.
- When marketing output keeps sounding generic or inconsistent.

When not to use: a one-off task where the user has already given full context in the request.

## Where it lives
A single markdown file in the repo or docs folder, for example `docs/product-marketing-context.md` (follow any existing convention; search for an existing file first and update it rather than creating a second one). Other marketing skills should read it before starting and propose updates when they learn something new.

## Gather first
Pull what already exists before asking anything: the homepage and pricing page, README, docs, sales decks, onboarding emails, reviews, support themes, customer research notes, analytics on who converts. Draft from those, then ask the user only to fill gaps or resolve contradictions. Present questions in one batch.

## Procedure
1. **Draft each section** below from sources, marking every statement as *confirmed* (stated by the user or evidenced in data) or *assumed* (your inference).
2. **Ideal customer profile.** Who gets the most value and buys most easily: company type or personal situation, size, role of buyer and user (they may differ), triggering events, current alternative. Add who is a bad fit and why; this is as useful as the ICP itself.
3. **Problem and jobs.** The job the customer is trying to get done, the pains with current approaches, and what it costs them in time, money or risk. Use customer words where available.
4. **Positioning.** The category or frame of reference, the main alternative (including doing nothing), the differentiating capabilities, the value those enable, and why it matters to this ICP. Finish with a one-sentence positioning statement.
5. **Messaging.** A headline-level value proposition, three or so supporting pillars, each with a proof point, and variations per persona if buyers and users differ. Note words and claims to avoid.
6. **Proof.** Customer quotes with permission status, case-study outcomes, metrics you can cite, logos you are allowed to show, awards, certifications. Mark anything that cannot be used publicly.
7. **Competitors.** Key alternatives, a one-line summary of each, where we win, where we lose, and the date this was last checked. Link to a fuller analysis if one exists.
8. **Pricing and packaging.** Plans, what drives the upgrade, common objections.
9. **Voice and style.** Tone, reading level, words we use and avoid, formatting conventions, examples of on-brand and off-brand sentences written fresh for this product.
10. **Customer language bank.** Verbatim phrases customers use for the problem and the outcome.
11. **Open questions and assumptions.** Everything still unconfirmed, so it can be resolved later.
12. **Metadata.** Last updated date, who confirmed it, and a change log of significant edits.

## Maintaining it
- Update when a product, pricing or market change happens, or after research reveals something new. Do not silently rewrite confirmed statements; propose the change and record it in the change log.
- Keep it short enough to be read in a few minutes. Link out to detailed research rather than pasting it in.
- Remove stale claims; an outdated context document misleads every downstream task.

## Pitfalls
- Writing aspirational positioning the product cannot back up.
- A generic ICP ("SMBs who want to grow") that excludes no one.
- Mixing internal confidential data into a file other tools or contractors will read; keep secrets out.
- Treating assumptions as confirmed because they were written down.

## Deliver
Write or update the file, then reply with: where it lives, which sections are confirmed versus assumed, the specific questions the user needs to answer, and what sources were used. If updating, summarise the diff in a few lines.

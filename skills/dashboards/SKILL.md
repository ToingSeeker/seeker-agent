# Dashboards

## When to use

The user wants an at-a-glance, explorable view of a dataset that they can open in a browser and share as a file. Not for adding a page to an existing web app (follow that app's stack and components instead), and not for a single chart (use the data-visualization skill if available).

## Gather first

- Who looks at it and what decision they make with it. This chooses the three to six KPIs that go at the top.
- The data source and refresh expectation: one-off snapshot, or regenerated by a script on a schedule.
- The filters that matter (date range, region, product, segment) and the default view.
- Constraints: must it work offline, without a CDN, inside email or a locked-down network? Is the data sensitive?

## Design

- **Top row:** KPI cards. Each shows the value, its unit, the period, and a comparison (vs. previous period or target) with direction. A number without a comparison rarely means anything.
- **Middle:** two to four charts that explain the KPIs: trend over time, breakdown by the main dimension, distribution if relevant.
- **Bottom:** a detail table with sorting and search, for people who want the rows.
- **Filters** in one visible bar; every component responds to them consistently. Show the active filter state and a reset.
- Prefer one clear layout over many tabs. Use a responsive CSS grid so it works on a laptop and degrades acceptably on a phone.
- Follow the visual rules from data visualization: honest axes, a colour-blind-safe palette, few colours, clear labels and a "data as of" timestamp.

## Procedure

1. **Prepare the data in a script.** Load, clean and aggregate in Python, SQL or Node. Validate totals against the source (for example, the sum of rows equals the known total). Keep the raw-to-dashboard transformation reproducible.
2. **Decide the data payload.** Embed the data as JSON inside the HTML. Pre-aggregate when rows are numerous; embedding a huge raw table makes the file slow. If the detail table needs many rows, cap it, or paginate in the browser.
3. **Choose the rendering approach.**
   - Zero dependencies: plain HTML, CSS grid, and inline SVG or canvas charts drawn by small functions. Most portable.
   - A charting library (e.g. Chart.js, ECharts, Plotly, Vega-Lite): inline the minified library into the file if it must work offline; a CDN link is simpler but fails without network.
   - Use one library, not several.
4. **Generate the file from a template.** Have the script write `dashboard.html` with the data injected, so regenerating is a single command. Escape data correctly when injecting into HTML/JS (serialize as JSON; never concatenate raw strings into script tags).
5. **Wire the interactivity.** A single state object (current filters) and one `render()` that recomputes every KPI, chart and table from the filtered data. This avoids components drifting out of sync.
6. **Handle edge states.** Empty filter results show a clear message instead of broken charts; missing values are labelled, not shown as zero; long category names truncate with a tooltip.
7. **Verify in a browser.** Open the file (or serve it locally), check the console for errors, apply each filter, and confirm the KPIs change and match an independent calculation for at least one filter combination. If a headless browser is available, take a screenshot and look at it.

## Quality bar

- Every number on the page can be traced to the script and the source.
- KPI definitions are written down, in a footnote or info tooltip (e.g. "Active users = users with one or more sessions in the period").
- Loads quickly, with no external requests unless agreed.
- Readable without explanation by the intended audience.

## Pitfalls

- Averages of averages across filtered groups. Recompute ratios from summed numerators and denominators.
- Time zones shifting daily buckets.
- Comparing a partial current period with a full previous one. Label it or compare like-for-like.
- Sensitive data embedded in a file that will be emailed around. Aggregate or anonymise, and ask the user before including personal data.

## Deliver

Lead with the file path and how to regenerate it (the exact command). List the KPIs with their definitions, the filters, the data's as-of date, and what you verified (console clean, filters checked, numbers reconciled against the source). Say what you could not check, such as specific browsers or very large data volumes.
